# RNG and time

<!-- mode: explanation -->

Pokémon Red does not have one seedable battle PRNG. It has a hardware-coupled ordinary generator and separate link-battle sequences that are intended to start equal but live in each cartridge's state. This distinction determines what the Lean simulator can honestly claim.

## Ordinary `Random`

`Random` is defined in `home/random.asm`:

```asm
Random::
    push hl
    push de
    push bc
    farcall Random_
    ldh a, [hRandomAdd]
    pop bc
    pop de
    pop hl
    ret
```

`Random_` in `engine/math/random.asm` updates two HRAM bytes:

```asm
Random_::
    ldh a, [rDIV]
    ld b, a
    ldh a, [hRandomAdd]
    adc b
    ldh [hRandomAdd], a
    ldh a, [rDIV]
    ld b, a
    ldh a, [hRandomSub]
    sbc b
    ldh [hRandomSub], a
    ret
```

This is not equivalent to a conventional recurrence over `hRandomAdd` and `hRandomSub` alone.

### Inputs that affect the result

- `rDIV` is read twice.
- The first addition is `adc`, so the carry flag entering `Random_` matters.
- The carry produced by that addition remains live until `sbc` and affects the subtraction.
- Bank-switch and wrapper instructions preserve flags along this path.
- Instruction timing determines the two divider values.
- Interrupt timing can run other code between gameplay operations.

A faithful instruction-level model therefore needs CPU flags, fetched-IR pipeline cycles, `DIV`, interrupts, and clock-domain phase. A source-level formula that ignores entering carry is incomplete. The standalone [`sm83-lean` package](../reference/sm83-semantics-package.md) supplies physical `LDH`/ADC/SBC/stack/call address/control/commit intent; the Pokémon adapter supplies T1F–T4R divider progression and a phase-indexed MMIO drive. A changing dynamic-bus read folds low bits over the sample window rather than sampling one timeless `rDIV` byte. The [microarchitecture contract](../reference/sm83-microarchitecture-contract.md) and [DMG-CPU B profile](../reference/dmg-cpu-b-profile.md) prevent de-overlapped fixture timing from being mistaken for that physical sample phase. Neither side alone determines `Random_`.

## VBlank continuously mutates RNG state

`VBlank` in `home/vblank.asm` calls `Random` once per frame after graphics transfers. Battle code frequently calls `DelayFrame`, `DelayFrames`, animation routines, text routines, and menu loops. Those presentation operations change how many VBlanks occur and therefore change `hRandomAdd`/`hRandomSub` before the next mechanics-visible random call.

This creates an important boundary problem:

- Omitting animations is desirable for an RL simulator.
- Omitting their elapsed frames changes the physical console RNG trajectory.
- Pretending that the fast simulator and console share a small seed would be false.

The proof must either execute exact timing or abstract the hardware observations explicitly. It cannot silently do neither. One concrete example is player switching: `RetreatMon` selects recall text from wrapped enemy-HP arithmetic before the enemy completes the turn, so different text paths alter divider/VBlank history even though the text is absent from the semantic event alphabet.

## `BattleRandom`

`BattleRandom` is defined at `engine/battle/core.asm:6543`.

### Ordinary battles

When `wLinkState != LINK_STATE_BATTLING`, `BattleRandom` jumps to `Random`. All hardware/timing considerations above apply.

### Link battles

When a link battle is active, `BattleRandom` reads this cartridge's byte list instead of `rDIV`.

The cable-club setup intends to use the internally clocked machine's list on both sides:

1. it generates ten random bytes, rejecting bytes greater than or equal to `$FD` but permitting zero;
2. it exchanges both machines' blocks;
3. the internal-clock side already aliases its generated bytes as the battle list;
4. the external-clock side scans the received block for the first byte that is not `0`, `$FD`, or `$FE`, then copies ten bytes while skipping `$FE`.

That scan skips legitimate leading zero random bytes. If the internal list begins with zero, the external side can shift its copied list and read beyond the intended ten-byte payload. Equality of the post-setup lists is therefore a normal-case invariant, not unconditional source behavior.

Although `SERIAL_RNS_LENGTH` is 10, the standard battle routine cycles the first nine entries:

1. return entry at current index;
2. increment the index;
3. for new indexes 1 through 8, return immediately;
4. after returning index 8, reset the index to 0;
5. replace each of the first nine seeds with `(5 × seed + 1) mod 256`.

Thus each cartridge perspective has:

```lean
structure LinkBattleRng where
  rawBlock : Vector UInt8 10
  index : Fin 9
```

plus the exact first-nine update boundary. A full link model contains two such states and proves equality only under explicit setup and equal-draw-history premises. The tenth post-setup byte remains in memory even though the standard battle cycle does not consume it.

Virtual Console conditional assembly changes the return path and is not covered by the initial Red cartridge proof.

## Not every battle random call uses `BattleRandom`

The initial audit found 54 direct `Random` or `BattleRandom` calls across the battle and adjacent files. They serve different purposes.

Examples using `BattleRandom`:

- equal-Speed order;
- failed escape tests, including the post-faint prompt whose speed input is always party slot 1;
- enemy move-slot selection;
- sleep, confusion, Disable, Bide, Thrash, trapping, and multi-hit counters;
- critical-hit and accuracy tests;
- damage randomization;
- Metronome and enemy/link Mimic choices;
- traded-Pokémon disobedience branches and replacement-move selection;
- wild DVs loaded inside battle;
- most move side-effect chances.

Examples using ordinary `Random` directly:

- trainer action AI in `TrainerAI` (a successful switch then chooses the lowest-index other living member without another draw);
- Safari escape in `StartBattle`;
- capture calculations in `ItemUseBall`;
- Safari bait/rock durations in item code;
- every VBlank.

Items and trainer action AI are disabled or different in link battles, so direct `Random` does not automatically imply a link synchronization error. The coverage manifest still needs to classify every call site and its reachability. Source-expanded byte boundaries are catalogued in [Battle probability thresholds](../reference/probability-thresholds.md).

## Exact random consumption is a mechanic

Many routines use rejection sampling. The number of bytes consumed is data dependent.

Examples:

- damage randomization rotates each returned byte right once, then repeatedly samples until the rotated value is at least 217;
- Metronome rejects 0, Struggle and above, and Metronome itself;
- Sleep rejects a zero sleep counter;
- move-slot selection uses initial 63/64/63/66 byte buckets and retries blank or disabled slots;
- capture restricts the first random byte to a ball-specific range;
- Teleport/Roar/Whirlwind sample within a level-derived range;
- player Psywave rejects zero while the enemy path does not.

A simulator that samples directly from the final mathematical range may match the marginal value distribution while consuming a different transcript. That breaks later outcomes and link synchronization. The high-level model must implement the same rejection loop or prove a transcript-preserving equivalent.

## Proposed formal interface

The verified battle core should request bytes rather than own a hidden mutable generator:

```lean
inductive RandomObservationSource
  | ordinary
  | linkPerspective

structure OrdinaryRandomRequest where
  site : RandomSite

structure RandomTranscript where
  ordinaryMechanicsResults : Stream UInt8
  linkInitial : Side → Vector UInt8 10 -- post-setup bytes for each perspective
```

This interface supports two proof levels.

### Transcript-parametric battle equivalence

The ROM does not request a finished ordinary byte from its environment; it computes one from CPU state and two divider reads. Therefore the low hardware trace and high semantic transcript cannot literally be the same stream.

Instrument the low-level runner at named mechanics-visible return sites. For each such call it records:

```text
(Random or BattleRandom, source label/site, returned byte)
```

A coupling relation supplies the projected ordinary results to the high-level core. Link results are compared with each perspective's deterministic first-nine transition rather than supplied as external responses. The transition theorem proves:

- the same projected source/site sequence;
- the same returned values at those sites;
- the same number of high-level mechanics requests;
- equal projected state/events;
- preservation of coupled, rather than byte-for-byte identical, remaining traces.

Presentation VBlanks may execute additional ordinary `Random_` calls. They remain in the low-level hardware execution and influence later recorded bytes, but they do not create high-level mechanics requests.

This is the first feasible and useful 1:1 mechanics theorem. Proved presentation summaries must preserve the hardware-trace effect and the location of the next mechanics-visible observation.

### Hardware RNG equivalence

Separately prove that the SM83/hardware model executes `Random_`, VBlank, divider updates, banked wrappers, and interrupt timing correctly. For a complete cycle-level cartridge trace, the environment provides controller/link/LCD timing and the machine derives the ordinary random bytes.

The instrumentation itself needs a theorem: every recorded ordinary result equals `hRandomAdd` returned by the decoded canonical routine, and no mechanics-visible call is omitted or duplicated. The episode refinement theorem can then be instantiated with the semantic projection produced by that machine execution.

## RL random provider

The RL hot path may provide ordinary bytes from a modern reproducible PRNG. The contract is:

- the same seed and reset configuration produce the same byte stream;
- transcript recording permits exact replay;
- the battle core consumes bytes exactly as the cartridge logic would;
- link mode uses each cartridge perspective's list update after initialization and does not query the ordinary provider per link draw;
- the provider is not advertised as reproducing Game Boy divider timing or its empirical distribution.

This separates two useful concepts:

- **mechanics fidelity:** the same byte responses cause the same battle behavior;
- **hardware-distribution fidelity:** the provider produces bytes with the same timing-dependent distribution as a physical console.

The project requires the first. The second belongs to hardware emulation research and is not required for RL training.

## Random-site inventory requirements

Each random call in the final coverage manifest records:

| Field | Description |
|---|---|
| source label | Assembly routine and ROM address |
| random function | `Random` or `BattleRandom` |
| mode reachability | wild, trainer, link, Safari, tutorial |
| purpose | accuracy, damage, AI, duration, selection, etc. |
| rejection rule | accepted byte predicate |
| output transform | masks, rotates, comparisons, arithmetic |
| consumption proof | theorem linking the projected low call trace to high responses and preserving trace coupling |
| regression vectors | boundary and multi-rejection traces |

## Required RNG regressions

At minimum, tests and proofs include:

- incoming carry 0 and 1 for `Random_`;
- divider changes between the two reads;
- VBlank updates between two battle call sites;
- equal-Speed boundary bytes;
- every [percent-macro threshold](../reference/probability-thresholds.md) at `threshold - 1`, `threshold`, and relevant surrounding branch boundaries;
- accuracy byte equal to threshold;
- Focus Energy/high-critical rotated bytes;
- damage randomization with multiple rejected bytes;
- Metronome with a run of invalid IDs;
- Sleep with repeated zeroes;
- disobedience rejection loops and random replacement-move retries;
- enemy slot boundaries `62/63/126/127/189/190` plus blank/disabled retries;
- trainer action-AI classes that consume direct `Random` but ignore it or take no action;
- a presentation VBlank `Random_` update that changes the next projected byte without adding a high-level request;
- player/enemy Psywave starting with zero in link mode;
- ninth link draw followed by all nine seed updates;
- cable setup with a leading zero and the resulting post-setup list mismatch;
- conditional link index/list equality after symmetric move paths and paired-state divergence after asymmetric paths;
- Safari and capture paths that use ordinary rather than per-perspective link RNG.
